二、实时字幕延迟 4.66 秒 → 3.35 秒（−1.3 秒，约 −28%）

窗口 20 秒 → 12 秒；节拍 3.0 秒 → 2.0 秒。

依据（60 秒素材，窗口**末尾对齐**逐词比对 —— 这个口径改了三版才对：
第一版比了长度不同的整段 ✗，第二版对齐开头比末尾 4 秒（落在不同时间点）✗，末版才对 ✓）：
- 12 秒窗口：**提交内容 0.0% 不同** ✓，每步识别 1.58 → 1.13 秒
- 8 秒窗口：开始听错（これまで → 声まで）✗
- 6 秒窗口：差异 5.4% ✗
- 节拍降到 1.5 秒**不再有额外收益** → 瓶颈已经不是周期量化，是「安全线 1.5 秒 + 每步识别 + 翻译」本身
- 装好后的默认值复验：延迟中位 3.35 秒、每步 1.09 秒 / 预算 2.0 秒、丢音频 0 次 ✓

拿掉的是**用不上的左文**：一句话最长 4 秒就切走了，20 秒窗口里大部分内容早就提交过。

顺带否掉两个方案（都是实测否的，不是猜的）：
- beam_size 5 → 1：每步只省 10~20%，但**识别文字变了**（8 个窗口 5 个不同，
  含一处「春ちゃん」写成「はるちゃん」）✗ —— 省得少 + 改了文本，不划算
- 译文缓存：实测 19 个项目 7433 条真实字幕，同句重复率只有 5.5%，且重复最多的是
  「うん(21) / はい(19) / そう(17)」—— 这些词的中文恰恰要看上下文（はい = 是 / 好 / 在 / 对），
  缓存会把第一次的译法固定下来 → 固化错译 ✗（跟「全局纠正表」是同一类坑）

九、纠正表：补上「お職」这一族写法，并新增「保护词」

**为什么补**：同一期同一个短语出现了两种译法，所以能确定是识别错 ——

```
#23   日「汚職大好き」→ 中「超爱贪污」      ✓ 对
#246  日「お職大好き」→ 中「超喜欢主职」    ✗ 错
```

原来的表只列了「お食…」5 种写法，**没有「お職」**。那期残留 4 处
（#246 / #1992 / #2122 / #3044），中文跟着错成"主职 / 职业 / 御职"。
表里现在多了 2 条：

```
お職警官 = 汚職警官
お職     = 汚職
```

**新增「保护词」**：表里左右写成一样的行，表示「这个词是正常的，别改」。

```
お職場 = お職場      ← 正文里的「お職場」（敬语版"工作单位"）原样保留
お職   = 汚職        ← 没有上面那行，「お職場」会被这条改成「汚職場」
```

为什么需要：替换是**子串**匹配 + 长的优先，写得越短的规则越容易咬进正常词里。
以前这种行会被 `parse_table` **静默丢掉** ✗ —— 使用者写了保护词、以为生效了，
其实根本没有。现在它真的生效，而且：
- 保护词不出现在"改了几处"的日志里（它本来就没改字，记进去只会让人以为改了）
- 同一个左边写了两次时，**真规则优先于保护词** —— 手滑写一行保护词，
  不会把后面那条真规则静默取消掉
- 「这句识别错了」自动写规则那条路**仍然拒绝**左右一样的写法
  （那条路是"改错"，写保护词没有意义；保护词是给人手写的）

**实测（拿真实那一期 3691 条跑的，验收线动手前就写死）**：

```
「お職」4 → 0                        ✅
「お尻」12 → 12（正常词，一个都不能动）  ✅
「お飾り」1 → 1（不是错写法，不加规则）  ✅
时间轴 / 中文一个字不动                ✅ 逐条比过
保护词：不加 →「汚職場に行く」✗；加了 →「お職場に行く」✓
改动正好 4 条，一条不多
```

顺带说明：这 2 条规则在**装着的 2.3 上就已经生效**（表是数据，读的时候现读）；
「保护词」这个功能才需要 2.4。

字幕工坊 2.3 更新内容（2026-10-14）
仓库：https://github.com/lin1024-star/zimu-studio

这一版是好几件事凑在一起的（上一版 2.2 是 10-11 发的，这些都不在里面）：

一、识别听错能自动改对（日文纠正表）

同一个音被识别成不同汉字，翻译就会跟着错。例：原音「おしょく」被写成「お食」，
中文翻成「吃饭」，而正确写法是「汚職」（贪污）。**换模型解决不了** ——
实测三个模型都写「お食」，因为音频里就没有区分这两个词的信息。

- 纠正表在数据根目录的「日文纠正表.txt」，一行一条：识别错的 = 改对的。
- 识别之后、翻译之前自动替换；**改完立刻生效，不用重启，不联网、不消耗 API**。
- 表不存在就什么都不做；只改日文原文，中文、时间轴、编号一个字都不动。
- 实测：某期素材里「お食」出现 19 处 → 全部改对；中文「吃饭」19 处 → 0 处。

二、「这句识别错了」：用中文告诉它哪里错了

**写规则之前会问：只对这一期，还是所有视频都用 —— 默认「只对这一期」。**

为什么改这个（2026-10-14 使用者发现的问题）：纠正表原来是**全局一张**，所有视频都套用 ✗
可"识别听错"多半是这一期的事，而**错的写法在别的视频里可能是正常内容**：
这一期把「多すぎ」听成「大杉」，一旦写进全局表，下一期真有个说话对象叫「大杉」（真实姓氏），
就会被**静默改成「多すぎ」**，中文跟着错，而他看不出来。

- 「只对这一期」：规则存在项目里（project.json 的 ja_fix_local），跟着这段素材走，
  换别的视频完全不受影响；重开这个项目、继续翻译，规则照旧生效
- 「所有视频都用」：才写进数据根目录的「日文纠正表.txt」——
  同一个说话人、同一个错反复出现时才值得这么选
- 范围选择框把风险写在选项旁边（「如果别的视频里真的说了『大杉』，也会被改掉，而你看不出来」）
- 判定规则不变：同一个错词已经有别的写法时**报冲突、绝不覆盖**

在字幕列表里选中一条 → 点「这句识别错了」→ 用中文写一句「应该是什么意思」
（例如「应该是贪污」）。软件会自己推出正确的日文、当场试翻一遍核对，
然后写进纠正表，并把本片同错的条目一起改对、中文重新翻。

为什么这样设计：实测**只给这一句让模型自己猜，0/5 全错**；
**给它「这一句 + 现在译文 + 你期望的中文」，5/5 全对**。
所以你的中文反馈就是那把钥匙 —— 你不用懂日文。
它拿不准时不会硬写：会弹窗把两种中文摆出来，由你决定用不用。

三、识别模型：自动检测 + 推荐 + 六个模型的长短处

设置页最下面新增「怎么选识别模型」：自动检测显卡和显存，给出一个推荐，
并把六个模型（tiny / base / small / medium / turbo / large-v3）的大小、速度、
质量、适合什么时候用并排列出来。**它只给依据，不会自动改设置** ——
想用哪个自己选，想一键采用推荐就点「用推荐的模型」。下拉框旁边也直接写着
当前模型要不要下载、速度几颗星、质量几颗星。

实测（6 分 22 秒素材，同一台机器、同一份术语表）：
- turbo 与 large-v3 在真正有分歧的 48 处里各赢 10 与 8，另有 30 处 12 次重听票数打平
  —— **两者准确度基本持平**
- turbo 整轮快约 1.9 倍（识别部分快 2.5~3 倍）
- large-v3 的长处是汉字写法更规范（時 / 本当に 这类写汉字而不是假名），代价是慢、吃显存
- small 实测会漏字、截断，只在配置很低时用；tiny / base 只适合先看效果

四、中文自检：翻译完之后再扫一遍

它解决的是这个很要命的问题：**翻译错了，你看不出来，照着错的意思把片子剪错。**
翻译完之后再扫一遍中文，把**可能翻错、会让你剪错**的句子挑出来：

- 专名被听错或乱猜：同一个音被写成另一个词，意思完全变了
- 中文不成话：「容易被误解和容易被误解是女主角吗？」这种
- 前后自相矛盾：前面说「我来解除翻译」，后面又说「我开下翻译」
- 词义变了：日文「入れる」在打字场景是「输入」，写成「加入」

**它报的是中文 —— 你不用懂日语就能判断。** 措辞不同不算问题，不报。

- 翻译完自动跑一遍；校对页有「中文自检」按钮，随时能重跑。设置页最后一行可以关掉。
- 结果是一整块可滚动的清单，每条完整写出：时间、中文、为什么可疑、日文原文。
- **双击某一条 → 主窗口选中那一条**，自检窗口留着（跳过的条目标 ✔、淡绿底），
  改完回来接着看下一条。它不会锁住主界面。
- **只报不改** —— 改还是你说了算。

花费：一期素材（100～150 条）大约两三分钱；两小时素材大约两毛到五毛。
关掉它不影响翻译和导出。

实测（两期真素材）：
- 素材甲 147 条（识别质量差）：召回 7/7 = 100%，报 12 处，其中 11 处核对成立
- 素材乙 112 条（识别质量好）：只报 3 处，3 处都是人工标注时也犹豫的真问题

为什么只做「发现」不做「自动改」：实测模型**擅长发现问题（17/17）、不擅长给正确写法（0/17）**
—— 除非把使用者的中文意思告诉它（那就 5/5）。所以自动改留给「这句识别错了」，
自检只负责把可疑的地方端到你面前。

  选了只会卡在“正在加载模型”然后报连接超时。有使用者连试 11 次，一个字都没识别出来。
- 现在主程序会自己下：先弹窗说明要下多少 MB（large-v3 约 3 GB），点“是”才下；
  显示进度，可中断，下次接着下，已经下好的部分不重下。只下这一次。
- 下载源按实测速度排序：魔搭 ModelScope 优先 → hf-mirror.com → huggingface.co。
  实测（20 MB 样本、国内直连）：魔搭 14.8 MB/s；hf-mirror 跑了 120 秒都没下完，差约 90 倍。
- 必须关掉 huggingface_hub 的 Xet：实测不关的话，接口地址换了镜像，文件本体仍旧去
  cas-server.xethub.hf.co 取，返回 401 Unauthorized——只改镜像地址根本下不下来。
- 下载前先花几秒探测线路，自动绕开已经失效的系统代理（代理软件没开、端口变了）。
- 每个模型单独存在 models\downloaded\<模型名>\，不同模型的 config.json / model.bin 不会互相覆盖。
- 设置里“识别模型”旁边直接标出本机已有哪几个；开始任务前先问，点“否”就不下载。
- 下载失败给的是能照做的中文提示，不再是一个 ConnectTimeout。

二、识别后自动整理轴（对应改进计划 1.1 / 1.2 / 1.3 / 1.6）
- 相邻条一字不差 → 合并；紧贴着的语气碎片（短于 0.5 秒、2 字以内）并入相邻条；
  拖音「ああああああ」→「ああ」。
- 实测素材（4 分钟 GTA 日语直播，60 条）：60 → 56 条，过短 7 → 5，重叠 0，拖音 1 → 0；
  逐条复核文本，未发现误伤。
- 长静音与剩下的过短条目只报告、不擅改：像「ほんと?」只有 0.34 秒但是完整台词，合并就是吞内容。
- 整理前的原文存进 project.json 的 axis_raw，在界面「待确认…」里可一键还原，
  已翻译的中文会按时间保留。
- 设置里可关闭（“识别后自动整理轴”），默认开启。
